# V21 界面响应调度与复位后联动说明

本轮用户确认 MLP 识别、虚拟手仍正常，所有页面和触摸变慢；MPU 已连接并校准，复位后尚未点击启用联动。机械手的原因可由状态机直接确认：`HAND_HOME_DONE` 持续保持六轴复位目标，`hand_run=1`，不会自行进入 MLP/HDC 跟随。这是复位与主动跟随两个独立阶段。本轮保留该行为；进入“机械手→动作映射→启用 PL 联动”后按有效 MPU、标定与映射执行。

## 响应调度

原 DMA 空闲循环在每次显示服务之前连续调用八次通道评分 worker，每次至多 128 个采样/FFT 步骤；未限制这项后台任务的累计运行时间。其实际板端开销尚无本次计时，不能断言它是所有变慢的唯一原因。

| 项目 | V20 | V21 |
|---|---|---|
| 同一空闲机会的优先级 | 连续评分后显示 | 显示后评分，中间复查采集 |
| 评分调用 | 连续 8 次，每次 128 步 | 每次机会至多 1 次，每次 32 步 |
| 普通页面评分额度 | 无累计时间限额 | 每 5 ms 最多使用 0.5 ms 后暂停新块 |
| 通道/数据页评分额度 | 无累计时间限额 | 每 5 ms 最多使用 1.5 ms 后暂停新块 |
| 机械手 ACK | 触发状态重绘 | 只处理协议，不触发重绘 |
| 刷新测量 | 请求次数和绘制耗时 | 另统计 VDMA 实际观察到的内容切换率 |

额度按真实计时器扣除，不依赖主机执行速度。单个 worker 调用可越过剩余额度，结束后停止启动新块，下一周期续算；包括小型频谱统计阶段，因此这不是硬实时截止保证。分块、额度和显示优先可能降低诊断更新速度，超时结果仍显示无新数据，不沿用旧分数。采样窗口、评分公式、FFT 数据、滤波、识别阈值、模型与 PWM 状态机均未改变。

## 验证

- `cpu_test.log`：生产 worker 的额度耗尽/续算、计时器回绕、单块公平调度、扫描内容更新率、ACK 不重绘及故障刷新；机械手同步复位、主动联动、停止、失效保护、HDC 和标定回归。
- `lcd_test.log`：800×480、1024×600 界面、触摸反馈、SD/HDC 模型库、通道评分、虚拟手和康复流程回归。
- `quality_test.log`、`numeric_validation.json`：评分边界/序号/冻结窗口保护、八路足够计算量下吞吐、独立 NumPy/SciPy 数值对照。吞吐测试保持每批计算步数不变；计时额度另测，不以主机耗时冒充 ARM 性能。
- `baseline/manifest.json`、`regression_sources.json`：改动前基线与本轮验证输入；发布验证逐项确认继承 V20 位流、XSA、FSBL、模型及控制实现，BOOT 再核对加载段。

尚未下载实板或写 SD；无法给出本轮实际 FPS 增幅。串口开启诊断 `d` 后，`[STAT] lcd content_fps10` 为画面内容更新率的十倍（例如 200 表示约 20 次/秒），不是面板扫描频率。`quality_calls` 为累计后台调用数，`chunk_max_us` 为实际最长评分块，`quota_us` 为当前每 5 ms 额度。静态页面内容不切换时该 FPS 为零是正常现象。若显示冻结、关闭或采集持续积压，统计不会代表正常交互性能。

## 使用

启动镜像：`build/boot/BOOT_20261030_HAND_CONTROL_HDC_DYNAMIC_UI_BUDGET_V21.BIN`。

复位只回到已保存的放松五指目标和掌部零位；启用联动前必须完成有效标定、放松/张手/握拳映射、静息校准与 MPU 校准。离开机械手页面继续沿用现有停止行为。
